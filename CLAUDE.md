# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Open-source pet project: a single-player Mahjong solitaire (match-two-tiles) game in Vue 3 + TypeScript + Vite. No backend, no accounts. The player types a name (1–15 chars) and a game starts immediately on the classic 144-tile "turtle" layout, rendered in a tilted pseudo-3D style on a green cloth table.

## Commands

```bash
npm install
npm run dev            # Vite dev server
npm run build          # vue-tsc type-check + production build to dist/
npm run typecheck      # vue-tsc only
npm test               # vitest run (all *.spec.ts under src/)
npx vitest run src/game/game.spec.ts          # single file
npx vitest run -t "dealSolvable"              # single test by name
```

There is no linter configured yet.

Deployment: every push to `main` runs `.github/workflows/deploy.yml`, which tests, builds with `BASE_PATH=/<repo>/` (read in `vite.config.ts`), and publishes to GitHub Pages at https://lukasstanislav.github.io/mahjong/. **Runtime asset URLs must go through `import.meta.env.BASE_URL`**, because a hard-coded `/foo` breaks under the Pages subpath.

## Game rules (source of truth for behaviour)

- Layout positions are fixed. Only the faces are randomly distributed, and each deal is **guaranteed solvable** (see below).
- A tile is **pickable** only if no tile lies on top of it and at least one of its long sides (left or right) is open.
- First pick highlights a tile. If the second pick matches, both tiles are removed. If it doesn't match, it becomes the new first pick. Clicking the selected tile again deselects it.
- Identical faces match. Exceptions: any flower matches any flower, and any season matches any season (`matchKey` in `src/game/tiles.ts`).

## Architecture

`src/game/` holds the pure logic, with no DOM access. It is unit-tested and is where rule changes belong:

- `layout.ts`: positions use **half-tile units** (a tile covers 2×2 cells, `z` = layer). This is how half-offset tiles (end caps, apex) are expressed without fractions. `isFree`, `covers` and `touchesSide` define pickability, and everything else depends on them.
- `layouts.ts`: all selectable layouts (`LAYOUTS`; Turtle wraps `turtleLayout()`). They're drawn with a small `Builder` in **tile** units (`tile`, `rect`, half-tile offsets allowed) and converted to half-tile units. Any even count up to 144 works (`dealSolvable` uses fewer pairs). `layouts.spec.ts` checks every layout: even count, no overlaps, every raised tile supported, and solvable deals across 20 seeds; it also prints stats (free tiles at start). `useGame.layoutId` picks the layout for the next deal; `App.vue` stores the choice (`mahjong.layout`) and redeals on change. The shapes are traditional but drawn from scratch; don't copy other programs' layout files, which are their (often GPL) content. Each layout has a `shape`. `'wide'` layouts are the classic, landscape ones. `'tall'` layouts (Lantern, Pagoda, Hourglass, Tower, and Turtle (tall), which is the Turtle with x and y swapped) are original portrait designs for phones. They stay within about 7 × 10 tiles, so tiles are about 44 px wide on a 390 px screen, versus about 22 px for the Turtle (Turtle (tall) is about 30 px). The menu groups layouts by `shape`. On a first visit with no saved choice, a portrait viewport gets `DEFAULT_TALL_LAYOUT`. `Builder.profile` draws symmetric shapes from per-layer row widths.
- `tiles.ts`: the 144-tile set as 72 matching pairs.
- `deal.ts`: `dealSolvable` simulates a game in reverse: it repeatedly picks two currently-free positions from the remaining layout, assigns them a pair, and removes them. The recorded removal order is a valid solution. It retries if the simulation strands itself. Don't replace this with a plain shuffle, which often produces dead boards.
- `useGame.ts`: the Vue composable that owns game state (`tiles`, `selectedId`, derived `freeIds`, `availablePairs`, `won`, `stuck`) and the `pick` rule.
- `hint.ts`: `findPairs` lists every matching pair among the free tiles. `randomHint` picks one at random, never repeating the previous pair when another exists. `useGame.hint()` stores it in `hintIds`, which any match or new deal clears. Both boards make hinted tiles float and bob (the 3D one eases `hintAmt` per tile; `HINT_*` constants in `BoardRenderer`). **Auto Help** lives in `App.vue`, since it's a UI policy: it fires `AUTO_HELP_START_MS` (5 s) after the board emits `ready`, and again after `AUTO_HELP_IDLE_MS` (30 s) without a click (`pointerdown` capture on the game `<main>`). It never replaces a hint that's showing, and stays quiet when won, stuck, or on the name screen. Both boards emit `ready` once per deal, when the tiles are laid: the intro finished, was skipped, or was disabled by reduced motion.
- `playerName.ts`: name normalisation and validation (Unicode letters and marks, digits, space, `_`, `-`; max 15 code points).

### Rendering

There are two boards with the same props and events (`tiles`, `dealId`, `freeIds`, `selectedId`, `showFree` → `pick`). `App.vue` uses the WebGL board when WebGL2 is available, otherwise the DOM board. The WebGL board is loaded lazily as its own chunk; three.js is about 140 kB gzipped.

**WebGL board** (primary): `src/components/GameBoard3D.vue` is a thin Vue shell around `src/three/BoardRenderer.ts`, which is imperative three.js with no Vue inside.
- World: the table is in the XZ plane, +Y up, and the camera looks down at about 55° from +Z. Layout half-tile units map to X/Z, and layer `z` maps to `Y = z * TH`, so tiles physically rest on each other. **Tile ids are layout indices and are used directly as instance ids.**
- Each tile is 3 `InstancedMesh`es sharing one instance matrix, with offsets baked into the geometry: a green back half (`RoundedBoxGeometry`), an ivory top half, and a face quad. A fourth, invisible box `InstancedMesh` is the raycast target (`Raycaster` ignores `.visible`), which keeps hover picking cheap.
- Faces: `src/three/atlas.ts` rasterises `public/tiles.svg` symbols into a canvas atlas at runtime, plus flowers and seasons as text. Cells are filled with `IVORY`, the same colour as the body material, so the quad is seamless. **Engraving:** `createAtlas` also returns a height texture derived from the colour atlas (`buildHeight`): ivory = surface, ink = engraved floor, ramped by `ENGRAVE_RAMP` and blurred by `ENGRAVE_SOFTEN` into sloped walls. It's the face material's `bumpMap` (`ENGRAVE_DEPTH` = `bumpScale`). The face shader patch must also set `vBumpMapUv` to the per-instance atlas cell, or the bump samples the wrong tile. It's bump only (shading, no displacement), so the relief shows as lit and shaded stroke walls that shift with the parallax tilt and the palm shade. Each cell gets its own copy of the sprite text, so per-tile recolouring is a string replacement on that copy. Bamboo (`s1–s9`) swaps `fill: #000000` for `BAMBOO_GREEN`; the file on disk stays unmodified. `MeshStandardMaterial.onBeforeCompile` injects the per-instance attributes `aCell` (atlas offset) and `aState` (selected, hover, dim tint). If you change three.js versions, check that the `#include <uv_vertex>` and `#include <map_fragment>` chunk names still exist.
- Animation is CPU-side. While anything moves, `updateMatrices` recomposes every instance matrix each frame. Removed tiles are collapsed to a zero matrix. The renderer only draws when something changed (`dirty`, an animation, or the tilt is still easing).
- The intro drop is scripted, not physics. `onLand` fires from the frame loop when a tile crosses `LAND_AT` of `DROP`, and the Vue shell plays the clack and dust. A click during the intro skips it. Removal (`sync` sees a tile disappear) fires `onLeave`, which triggers sparkles and the chime.
- **Parallax:** the pointer position (NDC) is exponentially smoothed. The table group rotates by up to `TILT_MAX` (about 4°) so that the side under the cursor rises toward the camera, plus a small camera orbit. It's off under `prefers-reduced-motion`.
- **Camera fit:** the distance comes from the projected extents of every tile's 8 corners (not a bounding box, whose top spans the whole area at the tallest stack's height and crops flat layouts), and the image is centred with a lens shift (`setViewOffset`). `FIT_FILL` and `VIEW_SHIFT_Y` are upper bounds: the effective fill is `min(FIT_FILL, 0.98 − 2·|VIEW_SHIFT_Y|)`, so tiles never leave the screen. The DOM fallback board computes its bounds per deal (`fitView`). `Raycaster` and `project()` already account for the shift.
- Lighting: a soft-edged `SpotLight` key, whose penumbra makes the vignette, casts the shadows (PCF). There's also a hemisphere light and a weak fill. The cloth is `MeshPhysicalMaterial` with `sheen` (fabric BRDF) plus a noise map.
- **Palm shadow** is a light cookie: `SpotLight.map` multiplies the key light by `public/palm-cookie.jpg`, projected through the spotlight's shadow camera, so it falls correctly in 3D on the cloth and on the tiles' tops and sides. three only applies light maps when `castShadow` is on. The texture is processed at load (`setupPalm`): it's downscaled to `PALM_RES` (which blurs out the source's wall grain), then levels map luminance to a light multiplier (`PALM_LEVELS` → `PALM_SHADOW..1`). **Sway** (`swayPalm`) rolls the shadow camera's `up` vector about the light axis and shifts its `setViewOffset`. That moves the pattern without moving the light, so the tiles' own shadows stay still. Because of the sway, the scene renders every frame; it's off under reduced motion. `palm-cookie.jpg` is a 1024² crop of the original photo `assets-src/palm_shadows.jpg`, which is kept outside `public/` so it isn't deployed.
- **Selection FX** (`src/three/SelectionFx.ts`, a group added to the table so it tilts with it):
  - Glow outline: an additive quad at the selected tile's top face. Its fragment shader evaluates a rounded-rectangle SDF of the tile top, giving a sharp rim inward, a softer one outward, and a faint halo, windowed to exactly zero before the quad border (otherwise a visible box appears).
  - Rays: a pool of particles emitted from random points on the top-face perimeter, moving outward along the edge normal and upward with drag. Each has a `Points` head and a `LineSegments` tail. Additive blending with vertex colours: black means dead, so there's no compaction.
  - `BoardRenderer.updateMatrices` captures the selected tile's current position, including the bob, so the effects track it exactly. Rays are off under reduced motion; the glow stays but doesn't pulse.
- **Match = flight, crash, disintegration.** When `sync` sees tiles disappear, `pairUp` groups them into matched pairs and `launchPair` gives each tile a `Flight`. Both tiles rise to `FLY_LIFT` (4 layers) above the higher of the two, and at least `FLY_CLEAR` over any stack between them (sampled from the heightfield). On the way up they back off (`FLY_WINDUP`), lean back and yaw so their local X axis lies on the line between them, so their long sides meet. Then they slam together, accelerating (`FLY_SLAM`, longer for distant pairs), lean in, and stop touching at the shared impact point. On impact, `crash` starts the dissolve there, spawns crumbs that spray outward from the impact point (`Debris.spawn`'s `origin`), and fires `onLeave` (the sound). The game state already dropped the tiles when the flight started, so play continues during it. The DOM board mirrors this with the `crash` keyframes (offsets from `crash()` in `GameBoard.vue`).
- **Disintegration.** On impact, the tile's per-instance `aDissolve` runs from 0 to `OVERSHOOT` over `LEAVE` seconds. `injectDissolve` (an `onBeforeCompile` on all three tile materials) discards fragments where the field `f = FIELD_NOISE·noise(local pos) + FIELD_HEIGHT·(1 − y/TH)` is below the progress, and makes a thin band above the threshold emissive (the hot, eaten edge). At the same time, `src/three/Debris.ts` spawns about 170 instanced crumbs per tile: low-poly icosahedra, mostly ivory with some green and ink. Each is released when the dissolve front reaches it (the same `dissolveField`), then moves ballistically with spin and gravity, and a strong velocity component **toward the camera** (`TOWARD_CAM`) makes it fly out of the viewport. Crumbs shrink to zero near the camera (`NEAR_FADE`) instead of clipping through the near plane. Crumbs collide with a **heightfield** (`rebuildHeightfield`/`groundAt` in `BoardRenderer`): a grid of `HF_CELL` cells holding the top of the highest *present* tile, or 0 for the cloth. It's rebuilt only on a deal and when a match starts, and dissolving tiles are already excluded. A crumb that drops below the surface after being above it last frame **lands** (it bounces up to `MAX_BOUNCES` times, then rests with `FRICTION`). One that was already below it has hit the **side** of a taller stack and is knocked back horizontally. Resting crumbs fall off when the tile under them is later removed. The debris sim assumes a sane `dt`: in headless/software rendering (~5 fps) the 0.05 s dt clamp slows physics against the lifetime clock, so step it manually at 1/60 s to test. The sound is `playCrumble` (tiny high-pitched grains of the clack samples) plus the chime. Known gap: the shadow depth pass doesn't discard, so a dissolving tile's shadow stays whole for `LEAVE` seconds.
- **Victory** (`src/three/Fireworks.ts`, in the table group). `sync` spots the final pair (the board goes from some present tiles to none): its crumbs are gold/red and thrown harder (`Debris.spawn(..., gold)`), and `fireworks.start` is queued for `LEAVE + CELEBRATE_DELAY` later. That runs an opening barrage, then a finale volley, then an idle shell every few seconds until the next deal (`clear()`). Shells launch from beyond the near edge and climb along an eased path. They burst toward the near side of the board, because raised points project higher on screen and the title occupies the top. Sparks are Points heads plus LineSegments tails, additive with RGBA vertex colours, and they land on the heightfield as embers. **Dusk:** additive light on the sunlit cloth washes every colour to yellow-green, so `fireworks.dusk` eases to 1 during a show and the renderer dims the key and hemisphere lights by it (`DUSK_SUN`, `DUSK_AMBIENT`). Each burst flashes a `PointLight`, which is always in the scene at intensity 0, because adding a light later recompiles every shader. Clicking the cleared table calls `launchAt`, a shell that bursts under the cursor at `CLICK_BURST_Y` (rate-limited). Everything is off under reduced motion. Sounds: `playLaunch`, `playBurst` and `playFanfare` in `sound.ts`, all synthesised. The overlay (title, name, Play again) and the fanfare live in `App.vue` and appear after `VICTORY_MS`. The overlay has `pointer-events: none` except on its button. The DOM board has its own 2D show (`ParticleLayer.firework`, with a CSS dusk vignette).
- **Testing the win:** in dev, `__mahjong.solve(ms = 120, leavePairs = 0)` plays the deal's recorded solution (`useGame.solveStep` → `solverPair` in `hint.ts`). For example, `solve(10, 1)`, then click the last pair yourself. Headless Chrome (`--headless=new`) renders this at 60 fps on macOS, so screenshots driven over CDP show real timing.
- Particles (landing dust) stay a 2D canvas overlay (`src/fx/particles.ts`), fed with projected screen coordinates.
- In dev builds only, `window.__mahjong = { board, props }` is exposed for automated browser checks.

**DOM board** (fallback): `GameBoard.vue` uses positioned `<div>`s, with thickness made from stacked `box-shadow`s (`--depth`), and `TileFace.vue` uses SVG `<use>` into `public/tiles.svg`. That sprite is a riichi set kept **unmodified**; every symbol begins with an unfilled `#tile` rect, so references must pass `fill="transparent"`. Draw order there comes from `z-index` (`z*10000 + (x+y)*100 + x`). Every keyframe and transition on `.tile` must keep `rotate(var(--rz))`.

**Sound** (`src/fx/sound.ts`): landing clacks are the one-shots in `public/sounds/` (`CLACK_FILES`). Each landing picks one at random and varies its pitch (playback rate), brightness (low-pass cutoff), level, start (tiny jitter) and stereo pan (the tile's screen x). The ranges per surface are in `SHAPE` (`'felt'` for layer 0, `'tile'` for upper layers). Only the first `slice` seconds play, because intro landings come every 28 ms. On load, every file is trimmed of leading silence (onset detection) so the hit lines up with the visual landing, and peak-normalised so the random choice doesn't jump in volume. Adding a take means adding its path to `CLACK_FILES`. `public/sounds/tap.mp3` is the **pick** sound (`playPick`, when a free tile is selected). **Ambience** (`src/fx/ambience.ts`): the source takes are about 8 s and not loopable, so it doesn't loop. It's a texture extender: one take is picked at random per session and only that file is fetched. It's trimmed (`EDGE_TRIM`) and RMS-normalised (`TARGET_RMS`), then played as an endless chain of `GRAIN`-second segments from random offsets, each re-pitched by `RATE`, joined by equal-power sin/cos crossfades (`XFADE`), and scheduled `LOOKAHEAD` seconds ahead on the audio clock. `unlockAudio` suspends the AudioContext while the tab is hidden, because throttled background timers would starve the queue. It has its own toggle (`setAmbienceEnabled`, stored in `localStorage`), and the global Sound mute silences it too. A **match** plays one of `MATCH_FILES` (`crumble-1/2.mp3`, about 1.6 s each after the onset trim) at random via `playMatch`. Both tiles of a pair call it, and it dedupes to once per pair. If the files are missing, it falls back to the synthesised `playCrumble` (grains of the clacks) plus `playChime`. If no clack file loads, a synthesised clack is used instead. The match chime and the blocked-tile honk are synthesised. `unlockAudio()` must be called inside a user gesture (`App.vue`'s `deal()` does this). The mute preference is stored in `localStorage`.

`App.vue` switches between the name form and the game. The last used name is remembered in `localStorage` (all access in try/catch).

## Constraints

- The player name is untrusted input. Only render it via text interpolation, never `v-html`.
- Keep game logic out of components so it stays testable in the `node` Vitest environment (no jsdom configured).
